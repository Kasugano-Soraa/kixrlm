# 原则：模型主导，证据约束，机制兜底

kixrlm 不是把人类组织图翻译成代理流水线。它让主模型根据任务属性选择做法：简单任务可以 solo，信息缺口值得补时引入工具或观察者，确有可分离工作时才组织协作。

参考实现的依据是 [`agent.cordis.yml`](../integrations/dsh/kixrlm/agent.cordis.yml) 中启用的 `persona-incentive`（第 121–165 行）与 [`kixparadigm/SKILL.md`](../integrations/dsh/kixrlm/skills/kixparadigm/SKILL.md)。同一配置文件前面的 persona 已禁用；保留的历史角色、Sprint 模板与流程说明不是普遍强制步骤。

## 1. 优化净收益，而不是流程完成率

选择行动时同时考虑：

> 有证据支持的目标达成，减去重要剩余不确定性、改动复杂度与回归风险，以及搜索、工具和编排成本。

这是判断准则，不是可精确计分的公式。下一步应当能改变决策或改善交付；更多角色、更多检查和更长解释不天然更好。停止条件也不只是“工具成功”：该做的检查完成后，继续工作的预期收益低于成本才停止；重要未知仍须披露。

## 2. 目标与前提先于实现

目标不清、影响大或不可逆、需求已指定实现方案时，检查：

- **XY：** 用户真正要解决什么？
- **前提：** 方案依赖的假设能否核实？
- **路径：** 有没有更直接、更低风险的办法？

只问会影响决策且上下文无法消解的歧义。明确、低风险、可逆的任务无需先走一套模板。挑战给出理由；用户裁决后执行，不反复争夺决定权。继续修补或交接时仍需保留用户目标，不能把旧 finding 清单当成完整验收。

## 3. 把执行、观察、结论分开

“三通道”是证据关系，不是三个固定代理：

| 通道 | 关心的问题 |
|---|---|
| 执行 | 做了什么，产出了哪些待验证断言？ |
| 观察 | 什么证据或反例能推翻重要断言？ |
| 汇总 | 证据实际支持到哪里，哪些未知影响交付？ |

重要断言需要与风险相称的独立证据。观察者应收到目标、约束、材料与待检验断言，而不是“帮我证明已经正确”的辩护。视角来自 prompt；同一模型的独立上下文仍可能共享盲点，跨厂商也不是正确性证明。涉及外部语义的重要断言应有跨厂商或可重放物证通道。

有效反例按可达性、契约和证据裁决，不能被多数 APPROVE 冲掉。失败、空输出和没读到材料都不是支持证据；不为凑票机械重派。测试通过只证明所覆盖的行为，LLM 判断不替代确定性检查。

## 4. 按依赖和风险组合，不固定角色

- 独立而足够重的工作可并行；小任务的分派成本可能比直接执行更高。
- 有顺序依赖的任务应沿依赖执行，不能假装并行后再由主线程修补交接。
- 角色名只是职责契约；协调与最终判断留在主线程，外部发布、破坏性操作不能由“流程走到这里”自行授权。
- 会改变实现方向的观察应先于相关编辑；最终验证要绑定材料版本，材料或依据变化后重判受影响的证据，不用旧结论替新版本背书。

现有 dev/qa/reviewer、kixpower Sprint 路径和 workflow 是参考实现中的选择，不是采用此方法的必选项。

## 5. 软指导与硬边界分别承载

| 层 | 适合承载 |
|---|---|
| 常驻 persona | 少量判断锚点、取舍准则 |
| 按需 skills | 任务方法、观察视角、低频说明 |
| 插件 / 宿主 hooks | 可机械检测的约束、门禁与生命周期检查 |
| memory | 有来源、有适用范围的经验，不是新的无限制指令 |

提示词不能替代强制 hooks；插件也只约束它实际接入的路径。尤其不能把原生工具策略扩大解释为 RLM 沙箱，详见 [安全说明](../SECURITY.md)。规则与常驻上下文都有成本，新机制必须用实际收益证明值得存在。

## 6. RLM 可选，经验需要边界

RLM 适合把长数据放进持久变量或文件，仅把决策需要的切片带回上下文；并不要求每个任务先启动 Python。单步、需审计的文件/shell 操作优先使用原生工具。内核重启会丢状态；内核内操作仍有宿主权限。

local/global 沉淀应小步、有证据、可追溯；“可回滚”不等于并发安全或隐私擦除。没有证据的经验不能升级为通用规则。

如何小步试用见 [合成场景](../examples/README.md)；如何在其他 Harness 保留这些边界见 [可移植性](PORTABILITY.md)。
